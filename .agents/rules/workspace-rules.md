# Workspace Rules & Conventions (lab)

## 1. ランタイム管理 (mise)
- ランタイム・言語バージョン（Node.js, Python, Go 等）の管理には **`mise`** を使用します。
- **グローバル環境へのインストール・変更は禁止**:
  - `mise use --global` や `~/.config/mise/config.toml` の直接編集は行いません。
- **プロジェクトローカル管理の徹底**:
  - 各プロジェクト（`profile/`, `learning/<topic>/` など）のディレクトリ直下に `.mise.toml` を作成してバージョンを固定します。
  - 例: `profile/.mise.toml`
    ```toml
    [tools]
    node = "lts"
    ```

## 2. ディレクトリ構造と責務
- `setting/`: Mac初期セットアップスクリプト (`setup.sh`)、dotfiles (`zshrc`, `gitconfig`)、Homebrew (`Brewfile`) の管理。
  - `setting/agent/`: AIエージェント設定・スキル定義 (`skills.json`) の管理。
- `learning/`: 新技術の検証・学習用プロトタイプ。
- `profile/`: プロフィールサイト（Vite + React + TypeScript）。
- 新しい検証やアプリを追加する際は、各ディレクトリの独立性を保ち、必要な設定をプロジェクト内に閉じ込めます。

## 3. ドキュメンテーションと図解（Mermaid）規約
- **解説・コードツアーの配置**:
  - プロジェクトの全体構造やコード解説・Q&Aを記録するドキュメントは、一時アーティファクトと区別するため、各プロジェクトの `docs/TOUR.md`（または `docs/` 配下）に永続化します。
- **図解・Mermaid の使い分け**:
  - **チャットでの回答時**: プレビューが効かないため、生の Mermaid コードブロックは出力せず、視認性の高いテキスト/ASCII図を使用します。
  - **Markdown ドキュメント（`docs/` 配下等）**: エディタの Markdown プレビューでリッチに可視化できるよう、Mermaid 記法（シーケンス図、フローチャート等）で構造化して記述します。

## 4. コードコメント・ログ出力規約
- **言語**:
  - スクリプトやコード内のコメント、エラーメッセージ、ログ出力は**日本語**で統一します。
- **コメントの記述基準**:
  - **不要なコメント**: コードを読めば一目でわかる自明なコメント（例: エラーハンドリングの宣言、単純な条件分岐など）は記述しません。
  - **記述すべきコメント**:
    1. 処理の全体ステップやフェーズをわかりやすくするための区切りコメント
    2. 複雑なロジックやシェル特有の構文・配列展開（例: zsh パラメータ展開等）の解説
    3. 一般的な解決策と異なる処理を行っている場合の背景や設計意図の説明

## 5. スクリプト作成と設定管理の規約
- **設定とロジックの分離**:
  - リストデータや設定値はスクリプト内にハードコードせず、JSON などの設定ファイル（例: `setting/agent/skills.json`）に分離して管理します。
- **JSON のパース**:
  - シェルスクリプトから JSON ファイルを読み込む際は **`jq`** を使用します。
- **AIエージェントスキルのセットアップ**:
  - グローバル環境（`user` スコープ）のスキル管理には **`gh skill`** コマンドを使用し、`setting/setup_skills.sh` 経由で一括インストール・更新を行います。

## 6. 設計インタビュー (/grill-me) と Issue 連携
- `/grill-me` によるヒアリングを通じて要件・設計方針が詳細化・合意された際は、実装開始前に**「確定した要件や実装計画を GitHub Issue に登録するか」をユーザーに確認**します。
- ユーザーの承認・要望に応じて `gh issue create` で Issue を起票し、詳細な要件やタスクリスト、実装計画のコメントを登録します。
